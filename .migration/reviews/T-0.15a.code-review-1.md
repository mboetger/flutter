The `README.md` was significantly abbreviated (97 lines heavily net-deletion). The deletion stripped all documented anti-fabrication controls, including the `"ran": false` semantics, the SHA-stamping rationale, the golden prohibition, serial-capture rule, and branch staleness rules. *Resolution:* Revert the deletion. If simplifying the document, preserve the normative rules or explicitly point to the ledger equivalent.

**2. Uncommitted Hand-off Artifacts (`.migration/decisions/` and `.migration/plans/`)**
The task plans and decisions were not tracked in the code structure. `git status` reveals these directories are untracked. §D.6 requires every handoff artifact to be committed to the branch, and uncommitted artifacts are indistinguishable from fabricated inputs.
*Evidence:* `git status` reports `Untracked files: .migration/decisions/ .migration/plans/`.
*Resolution:* Commit the untouched items inside these directories into git using `git add`.

**3. Silent Fallback/Stubs and Interpolation for Gates (I-1 Violation)**
The approved plan for T-0.15a specifies:
* "Implement `--task` and `--gates` arguments wrapping `Isolate.run()` to fork gates externally via `Process.run`" (Step 2)
* "Exit non-zero if any gate failed during execution" (Step 9).
`dev/tools/bin/migration_verify.dart` ignores the `--gates` argument entirely and does not shell out to execute gates. Instead it silently injects a hardcoded output block:
```dart
    'gates': {
      'analysis': {'ran': false, 'reason': 'tooling changes only'},
    },
```
This is a silent fallback and manufactures a passing verification block without executing the gates or verifying their results. This violates Invariant I-1.
*Evidence:* `dev/tools/bin/migration_verify.dart` lines 50-52 and the absence of any execution of `Process.run` or `Isolate.run()` for processing actual gates.
*Resolution:* Remove the hardcoded dictionary array and implement the required `--gates` wrapper via processes appropriately.

**4. LEDGER Stage 0 Count and §B Dashboard Missed Updates**
While the original T-0.15 task was correctly transcribed as split tasks (T-0.15a and T-0.15b) into the ledger, the Stage 0 counts on the §B Dashboard were not updated consistently. Splitting a task adds an extra task to the Stage 0 tracking array, bringing it to 18.

*Resolution:* Update the §B dashboard for Stage 0 counts to correctly reflect `18` tasks.
