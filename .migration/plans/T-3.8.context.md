# Context: T-3.8 — Replace `shell_->Spawn(...)` with FlutterEngineSpawn Seam behind Flag

## Problem Statement
In the legacy Android embedding, spawning an engine isolate from an existing engine is performed through direct `shell_->Spawn(...)` calls inside `AndroidShellHolder`.
In the standard Flutter Embedder API, engine spawning is exposed via:
- `FlutterEngineSpawn(parent_engine, const FlutterEngineSpawnConfig* config, FlutterEngine* engine_out)`

## Scope of Changes
1. `engine/src/flutter/shell/platform/android/android_shell_holder.h`:
   - Declare public method:
     ```cpp
     FlutterEngineResult SpawnEngine(
         const FlutterEngineSpawnConfig* config,
         std::shared_ptr<PlatformViewAndroidJNI> jni_facade,
         std::unique_ptr<AndroidShellHolder>* spawned_holder_out) const;
     ```
2. `engine/src/flutter/shell/platform/android/android_shell_holder.cc`:
   - Update `AndroidShellHolder::Spawn(...)` to branch on `settings_.android_embedder_api`.
   - On flag-on path: emit `TRACE_EVENT1("flutter", "AndroidShellHolder::Spawn", "path", "embedder_api")`, construct `FlutterEngineSpawnConfig`, and route through `SpawnEngine(...)`.
   - On legacy path: emit `TRACE_EVENT1("flutter", "AndroidShellHolder::Spawn", "path", "legacy")` and execute legacy `shell_->Spawn(...)`.
   - Implement `SpawnEngine(...)` with argument validation, child shell spawning, and population of `spawned_holder_out`.
3. `engine/src/flutter/shell/platform/android/android_shell_holder_unittests.cc`:
   - Add unit tests verifying legacy spawn path, embedder API spawn path, direct `SpawnEngine` invocation, and argument validation.

## Non-goals
- Composition mode migrations (scheduled for T-3.T1 - T-3.T6).
- Changes to FlutterJNI or Java embedding APIs.
