## 2. Documented Falsification Attempts

### Falsification Attempt 1: Proc Table Layout and Backward Compatibility
- **Hypothesis:** Appending fields to `FlutterEngineProcTable` will cause out-of-bounds writes when older embedders pass an earlier struct size to `FlutterEngineGetProcAddresses`.
- **Investigation:** `FlutterEngineGetProcAddresses` uses `STRUCT_HAS_MEMBER(table, member)`, which checks `offsetof(FlutterEngineProcTable, member) + sizeof(table->member) <= table->struct_size`. If an older embedder passes a smaller `struct_size`, the new members are not touched.
- **Result:** Falsified. Proc table extension is fully backward compatible.

### Falsification Attempt 2: Inertness for Non-Android Embedders
- **Hypothesis:** Adding dynamic thread merging fields to `FlutterCompositor` could inadvertently affect desktop or iOS compositors.
- **Investigation:** All existing embedders zero-initialize `FlutterCompositor`. With zero-initialization, `supports_dynamic_thread_merging` is `false`. When false, `EmbedderExternalViewEmbedder` in T-1.18b will not create a merger, preserving existing desktop and iOS behavior exactly.
- **Result:** Falsified. Zero-initialization guarantees 100% inertness.

### Falsification Attempt 3: Lifetime and Thread-Safety of Merger Handle
- **Hypothesis:** Embedders could retain `FlutterRasterThreadMergerRef` beyond the callback lifecycle, leading to dangling pointers or use-after-free.
- **Investigation:** The C-API documentation in `embedder.h` explicitly defines the lifetime contract: valid ONLY for the duration of the callback to which it is passed, and embedders MUST NOT store or retain the pointer. Furthermore, the wrapper in `embedder.cc` validates null pointers safely.
- **Result:** Falsified. Contract is explicitly documented and null-safe.
