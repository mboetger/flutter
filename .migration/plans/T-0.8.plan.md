## Implementation Sequence
1. Current-state analysis:
   - Android: `PlatformMessageHandlerAndroid::DoesHandlePlatformMessageOnPlatformThread()` returns `false` (`platform_message_handler_android.h:23`). Called on UI task runner by `Shell::OnEngineHandlePlatformMessage`. Immediate JNI call into `DartMessenger.handleMessageFromDart`.
   - iOS: `PlatformMessageHandlerIos::DoesHandlePlatformMessageOnPlatformThread()` returns `false` (`platform_message_handler_ios.mm:96`). Dispatches directly to custom `task_queue` or `dispatch_get_main_queue()`.
   - Ground truth evidence from T-0.4 characterization test `platform_message_affinity_unittests.cc`.
2. Why `false` is essential:
   - Background `TaskQueue`s (`BinaryMessenger.makeBackgroundTaskQueue()`) bypass the platform main thread entirely.
   - Forcing a hop through the main thread causes UI jank, thread contention, latency doubling, and head-of-line blocking when the main thread is occupied by view hierarchy operations.
3. Evaluation of options:
   - Option A: Android conforms to `true` (rejected: breaks background TaskQueues and observable behavior).
   - Option B: Embedder API grows an explicit configuration knob / proctable entry (recommended: preserves Android/iOS behavior, zero-initialized safe default `true` preserves desktop embedders).
   - Option C: Change Embedder API default to `false` (rejected: breaking change for existing desktop embedders expecting main thread dispatch).
4. Proposed C-ABI design for Stage 1 (Task T-1.13):
   - Add `bool does_handle_platform_messages_on_platform_thread` or an extended platform message callback in `FlutterCustomTaskRunners` / `FlutterProjectArgs`.
   - Forwarding through `PlatformViewEmbedder` to configure its internal `PlatformMessageHandler`.
5. Decision Record and §D.9 logging:
   - Record `DR-0020` selecting Option B.
   - Append iOS owner review entry to `.migration/HUMAN_REVIEW_REQUIRED.md`.
