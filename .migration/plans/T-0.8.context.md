# Context: Task T-0.8 — SPIKE: Platform Message Thread Affinity (Blocker B-3)

## Problem Statement
In the current Android embedder:
`PlatformMessageHandlerAndroid::DoesHandlePlatformMessageOnPlatformThread()` returns `false` (`platform_message_handler_android.h:23`).
Similarly, in iOS:
`PlatformMessageHandlerIos::DoesHandlePlatformMessageOnPlatformThread()` also returns `false` (`platform_message_handler_ios.mm:96`).

In contrast, the Embedder API's implementation in `PlatformViewEmbedder::EmbedderPlatformMessageHandler`:
`DoesHandlePlatformMessageOnPlatformThread()` returns `true` (`platform_view_embedder.cc:34`), and `HandlePlatformMessage` automatically posts to `platform_task_runner_`.

If Android naively adopted the Embedder API without addressing this:
1. Every message sent from Dart across a platform channel would hop from the engine UI thread to the Android main (platform) thread before invoking the Java handler.
2. Background `TaskQueue`s (`BinaryMessenger.TaskQueue` / `makeBackgroundTaskQueue()`), an officially documented Flutter feature designed to offload heavy computations, I/O, database queries, and network requests from the Android main thread, would be forced to hop through the main thread: `UI thread -> Platform main thread -> Java Background Executor`.
3. If the Android main thread is busy or blocked (layout, frame rendering, view inflation, GC), background channel dispatch would be stalled behind the main thread.
4. Channel latency would double, and high-frequency channel traffic would cause main thread contention and dropped frames.

## Governing Invariants & Principles
- **Criterion 1 (Preserve observable behavior exactly):** Background channel handlers must not be degraded or forced to hop through the main thread.
- **Criterion 5 (Generalize to other embedders):** The solution must serve both Android and iOS (`FlutterEmbedderAPIBridge`).
- **Criterion 6 (Narrower API surface / smaller diff):** The C-ABI addition to `embedder.h` must be clean, versioned, and backward-compatible.
- **I-1 (No silent fallbacks):** Explicit configuration, zero-initialized safe default (`true` for legacy embedders).
- **§D.9 (Human review required):** Log the iOS review entry in `HUMAN_REVIEW_REQUIRED.md`.
