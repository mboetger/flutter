### ROUND 2 RE-PLAN DISPOSITIONS

- **1. Total Virtualization Creates Elaborate Scaffolding (Honest Path Too Expensive):** `accepted-disputed`. Dropping the unit tests entirely and relying solely on the Validator is an invalid remedy to testing cost. Deleting tests violates invariant I-4 and establishes a toxic precedent (DR-0007). This failure is raised under a new blocking finding below.
- **2. Residual Path to Real Executables in T-0.15b:** `accepted-resolved`. The plan explicitly mandates routing `git log` and `adb` operations strictly through the `SystemCommandExecutor`. Because unit tests run on `FakeSystemCommandExecutor`, the test logic firmly sequesters `adb` and cannot reach or stall on a physical device.

### BLOCKING FINDINGS

**1. DR-0007 Violates I-4 and Causes a Reverse Failure Hole**
The planner resolved the expense of total virtualization by deleting the unit tests for `--audit-stack` and `--device-lock` via DR-0007. This creates a severe "reverse failure" vulnerability: an implementer can supply empty stub functions for T-0.15b, and the entire unit test suite will pass perfectly, meaning a structurally broken tool would be certified by the Code Reviewer.
"The Validator will catch it" is a schedule constraint, not a unit test mechanism. Furthermore, establishing a precedent in DR-0007 that difficult tests can simply be delegated away jeopardizes the rigor of the subsequent ~100 branches in this migration.
**Resolution:** Revert DR-0007 and reinstate the `--audit-stack` and `--device-lock` tests into the I-4 Parity section. To make honest testing undeniably cheaper without compromising the sandbox:
- **For `--audit-stack`:** Radically simplify the mock surface by decoupling data retrieval from evaluation. Architect a pure validation function `validateStack(List<String> mockGitLog, FileSystem fs)` so the test merely passes a List of strings rather than building a stateful `FakeSystemCommandExecutor` Git behavior interceptor.
- **For `--device-lock`:** Grant a narrow, explicit exception allowing the use of a real `Directory.systemTemp` path strictly for testing file-locking physics across Dart `Isolate` boundaries. Explicitly ban the lock test from touching `.migration/` or navigating to the real repository.

### GOVERNING QUESTIONS ANALYSIS

- **Can the suite be made green by touching anything outside `dev/tools/`?** Assuming the lock exception correctly restricts interactions to isolated system temporary directories, the unit tests remain securely enclosed.
- **Can the suite be fully green while the real tool does not work at all?** *YES.* Under the Round 3 plan, because DR-0007 deleted the testing requirements for T-0.15b, the test suite only exercises T-0.15a's logic. If T-0.15b is left functionally empty, the test suite executes perfectly (green) while the tool itself fails completely during a real integration run.
