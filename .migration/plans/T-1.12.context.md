# T-1.12 Context: Custom Task Runners & Thread Priority Setter

## 1. Problem Statement
Flutter's core architecture requires four primary task runners (`flutter::TaskRunners`): Platform, UI, Raster, and IO. The Embedder C-API (`embedder.h`) exposes `FlutterCustomTaskRunners` in `FlutterProjectArgs` to allow embedders to supply custom task runners or customize engine thread creation.

Multiple critical architectural gaps and discrepancies were identified in the Android Embedder API Migration Plan (`MIGRATION_PLAN.md` §1.12, `MIGRATION_LEDGER.md` §T-0.3, §T-1.12, and §T-2.5):

1. **Missing Custom IO Task Runner (`io_task_runner`):**
   `FlutterCustomTaskRunners` currently defines `platform_task_runner`, `render_task_runner`, and `ui_task_runner`, but lacks `io_task_runner`. In `embedder_thread_host.cc`, the code states:
   ```cpp
   // The IO threads are always created by the engine and the embedder has
   // no opportunity to specify task runners for the same.
   ```
   Embedders requiring full thread ownership (or running in thread-constrained environments) cannot supply a custom IO task runner.

2. **The IO Thread Priority Discrepancy:**
   When the engine manages the IO thread (in both engine-managed and embedder-managed thread hosts), `EmbedderThreadHost` hardcodes `fml::Thread::ThreadPriority::kBackground` (nice 10). Android's native embedder (`AndroidShellHolder.cc`), however, explicitly configures `host_config.io_config` with `fml::Thread::ThreadPriority::kNormal` (nice 0). Because the engine hardcodes `kBackground`, `thread_priority_setter` receives `FlutterThreadPriority::kBackground`, causing a silent thread priority regression for IO tasks on Android. Embedders must be able to specify the priority of engine-managed IO threads (e.g. `kNormal` for Android).

3. **Lack of User Data Context in `thread_priority_setter`:**
   `FlutterCustomTaskRunners::thread_priority_setter` takes only `void (*thread_priority_setter)(FlutterThreadPriority)`. It does not accept a `void* user_data` context. Embedders requiring instance state or JNI environment access cannot safely contextualize the callback without relying on brittle, process-global state.

4. **Missing Per-TaskRunner Thread Priority & Setter in `FlutterTaskRunnerDescription`:**
   Custom task runner threads are created by the embedder, so the engine's internal `fml::Thread` creation callbacks do not execute on them. `FlutterTaskRunnerDescription` lacks a priority field or priority setter callback. Embedders providing custom task runners need to associate a thread priority and priority setter callback with each runner, which can be invoked upon runner initialization or runtime priority adjustments (`EmbedderTaskRunner::SetThreadPriority`).

5. **Unsafe Struct Access in Existing `embedder.cc`:**
   In `embedder.cc`, line 2826 previously accessed `custom_task_runners->thread_priority_setter` directly without `SAFE_ACCESS`, risking out-of-bounds reads on truncated structs.

### v7 Prototype Failure Analysis
In migration v7 commit `555c6edd73a6`, an attempt was made to extend thread priorities, but it suffered from fatal defects:
- It inserted preprocessor-conditional struct padding (`#if UINTPTR_MAX == ...`) in `embedder.h`, violating C-ABI hygiene.
- It used hard struct size checks (`description->struct_size < offsetof(...)`), violating Rule 2 (`never struct_size < sizeof(...)`).
- It completely ignored `io_task_runner` and the IO thread priority discrepancy, leaving `SetIOConfig` hardcoded to `kBackground`.

## 2. Constraints & Invariants
- **C-ABI Backward & Forward Compatibility (§6.1 Rule 1, 2, 3):**
  - Append-only to `FlutterTaskRunnerDescription` and `FlutterCustomTaskRunners`.
  - All struct field reads must use `SAFE_ACCESS`. Never check `struct_size < sizeof(...)` or `struct_size < offsetof(...)`.
  - No conditional preprocessor directives (`#if UINTPTR_MAX...`) inside public ABI struct definitions.
  - `FLUTTER_ENGINE_VERSION` invariant: left at `1` (must never be bumped per `v7-post-mortem.md` §4.1).
  - Legacy zero-initialized structs must maintain 100% backward compatibility: `io_task_runner` defaults to nullptr (engine creates IO thread), `io_thread_priority` defaults to `kBackground`, and older `thread_priority_setter` is invoked if present.
- **Layering & Scope (§A.1 I-9, I-10):**
  - Scope strictly limited to `shell/platform/embedder/`.
  - No changes to `shell/common/`, `runtime/`, `lib/ui/`, or other platform embedders.
  - Zero Android types, NDK headers, or `#if defined(__ANDROID__)` in `shell/platform/embedder/`.
- **No Silent Fallbacks (I-1):**
  - If an embedder provides `io_task_runner` with invalid callbacks (e.g. missing `post_task_callback`), abort engine initialization and log an error rather than silently falling back to an engine-managed IO thread.
- **Testing & Verification:**
  - Host unit tests in `embedder_unittests.cc` covering:
    - Custom `io_task_runner` specification and task execution.
    - Custom task runner priority specification and per-runner priority setter invocation.
    - Engine-managed thread priority configuration with `thread_priority_setter_with_user_data` and context propagation.
    - Resolution of the IO thread priority discrepancy: configuring `io_thread_priority = kNormal` ensures the engine sets `fml::Thread::ThreadPriority::kNormal` and calls the setter with `kNormal`.
    - Runtime thread priority changes via `EmbedderTaskRunner::SetThreadPriority`.
    - Truncated struct compatibility via `SAFE_ACCESS`.
