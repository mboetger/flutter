# T-1.8 Context: Window Metrics Gaps (Padding, Gesture Insets, Touch Slop, Display Features, Corner Radii)

## 1. Problem Statement
The Flutter engine defines rich window metrics in `flutter::ViewportMetrics` (used to populate Dart's `PlatformDispatcher.views` and `MediaQueryData`), including physical view padding (safe area / cutout insets), system gesture insets, physical touch slop, display cutout/hinge features (bounds, type, state), and physical display corner radii.
In the legacy Android embedder, `FlutterJNI.nativeSetViewportMetrics` transfers 30 parameters directly into `flutter::ViewportMetrics`.
However, the Embedder API struct `FlutterWindowMetricsEvent` currently only exposes basic dimensions (`width`, `height`, `pixel_ratio`, `left`, `top`), `physical_view_inset_*`, `display_id`, `view_id`, and size constraints.
All of the following parameters are absent from `FlutterWindowMetricsEvent`:
- Physical padding (top, right, bottom, left)
- System gesture insets (top, right, bottom, left)
- Physical touch slop
- Display features (count, bounds, type, state)
- Physical display corner radii (top-left, top-right, bottom-right, bottom-left)

Without these fields in `FlutterWindowMetricsEvent`, any embedder relying on the Embedder API is unable to convey display cutouts, safe areas, edge-to-edge system bars, gesture navigation insets, touch slop, fold/hinge posture, or display corner radii. This causes `MediaQuery.padding`, `MediaQuery.systemGestureInsets`, and foldable hinge awareness to be zeroed or lost.

The authoritative contract established in T-0.4 (`android_viewport_metrics_unittests.cc` and `MIGRATION_LEDGER.md` §T-0.4, §T-1.8) lists all 30 parameters, requiring a 1:1 destination in `FlutterWindowMetricsEvent` for all metrics fields.

## 2. Constraints & Invariants
- **C-ABI Backward Compatibility (§6.1 Rule 1 & Rule 2):**
  - Append all new fields to the end of `FlutterWindowMetricsEvent`.
  - In `embedder.cc`, use `SAFE_ACCESS` with appropriate fallbacks (`0.0` for padding and gesture insets, `-1.0` for touch slop and corner radii where `< 0` represents unset).
  - Do NOT bump `FLUTTER_ENGINE_VERSION` (§G.5, §G.9 Item 2). Forward/backward compatibility is managed strictly via `struct_size` and `SAFE_ACCESS`.
  - Introduce `FlutterDisplayFeatureType` and `FlutterDisplayFeatureState` enums before `FlutterWindowMetricsEvent`.
- **Validation (§6.1 Rule 7):**
  - Validate physical padding values: must be non-negative and must not exceed window dimensions (`physical_height` or `physical_width`).
  - Validate display features: if `display_features_count > 0`, buffers must not be null, and count must not overflow `SIZE_MAX / 4`.
- **Layering & Scope (§A.1 I-9, I-10):**
  - Stage 1 is restricted strictly to the embedder layer: `shell/platform/embedder/`.
  - Do NOT touch Android platform code (`shell/platform/android/`). Android mapper adoption belongs to Stage 2 / Stage 3.
  - No Android-specific naming or semantics; display features, padding, safe areas, and corner radii are platform-agnostic concepts across Android, iOS, and desktop.
- **Testing & Verification:**
  - Host unit tests in `embedder_unittests.cc` covering:
    - Validation of invalid window metrics (negative padding, excessive padding, non-zero display features with null buffers).
    - Successful dispatch of window metrics with all parity contract fields populated with non-default values.
    - Backwards compatibility when sending window metrics with legacy struct sizes.
