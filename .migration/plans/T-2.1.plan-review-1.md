## 2. Documented Falsification Attempts

### Falsification Attempt 1: Infinite Recursion Risk if `platform_view_` is Defaulted to `this`
- **Hypothesis:** Initializing `platform_view_ = this` might seem convenient to avoid null checks, but calling `platform_view_->NotifyDestroyed()` would trigger virtual dispatch back to `PlatformViewAndroid::NotifyDestroyed()`, resulting in infinite recursion and stack overflow.
- **Investigation:** In C++, virtual dispatch on a base class pointer resolves to the most derived class override unless explicitly qualified (`PlatformView::NotifyDestroyed()`). Therefore, `platform_view_` MUST NOT default to `this`. Initializing `platform_view_ = nullptr` and checking `if (platform_view_) platform_view_->NotifyDestroyed(); else PlatformView::NotifyDestroyed();` avoids virtual self-dispatch completely.
- **Result:** Falsified. Null pointer initialization with explicit fallback prevents infinite recursion.

### Falsification Attempt 2: Impact on Surface Teardown Order During `NotifyDestroyed`
- **Hypothesis:** Forwarding `NotifyDestroyed()` through the delegate before tearing down `android_surface_` might change teardown timing or alter raster thread resource release order.
- **Investigation:** Currently in `PlatformViewAndroid::NotifyDestroyed()`, the first line is `PlatformView::NotifyDestroyed()`, followed immediately by the raster task to call `surface->TeardownOnScreenContext()`. Forwarding to `platform_view_->NotifyDestroyed()` maintains this exact sequence: notifying the engine shell delegate first, then executing surface teardown on the raster thread.
- **Result:** Falsified. Lifecycle sequencing and thread affinity remain identical to the characterization baseline.

### Falsification Attempt 3: Inadvertent Breakage of Subsequent Stage 2 Tasks
- **Hypothesis:** Exposing `SetPlatformView(PlatformView*)` might conflict with later tasks when `PlatformViewEmbedder` is introduced in T-2.3 or when inheritance is severed in T-2.4.
- **Investigation:** `PlatformViewEmbedder` is a subclass of `PlatformView`. In T-2.3, `on_create_platform_view` will construct `PlatformViewEmbedder` and pass it to `SetPlatformView`. In T-2.4, when `PlatformViewAndroid` no longer inherits from `PlatformView`, the `else` branch fallback (`PlatformView::NotifyDestroyed()`) is removed and `FML_DCHECK(platform_view_)` is asserted. The seam introduced in T-2.1 is precisely designed for this incremental migration.
- **Result:** Falsified. The design directly enables T-2.2, T-2.3, and T-2.4 without rework.
