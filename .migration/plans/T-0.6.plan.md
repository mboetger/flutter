## Implementation Sequence
1. Current-State Analysis:
   - Detail `AndroidContextDynamicImpeller`, `AndroidContextVKImpeller`, and `AndroidContextGLImpeller` responsibilities and timing (`shell/common/shell.cc:323`).
   - Identify how driver workarounds (Huawei, MediaTek, Exynos, emulators) are probed.
2. Evaluation of Architectural Options:
   - **Option A — Hoist Decision:** Embedder probes Vulkan capability and selects Vulkan vs OpenGL ES *before* `FlutterEngineInitialize`.
   - **Option B — Lazy Renderer Config:** Embedder API extended with `kDynamic` renderer type and raster-thread resolver callback.
   - **Option C — Invert Ownership / Embedder Adoption:** Embedder adopts engine-created Vulkan instance/device or engine provides context factory.
3. Comparative Analysis & Tie-Break:
   - Evaluate against `MIGRATION_PLAN.md` §10.1 criteria:
     - Criterion 1 (preserve behavior): Option A preserves all existing probe logic.
     - Criterion 5 (generalization): Option A matches iOS (`MTLDevice` passed into config) and desktop embedders.
     - Criterion 6 (narrow API surface): Option A requires zero new C-ABI surface in `embedder.h`.
4. Spawn & Engine Groups:
   - Document how `FlutterEngineSpawn` and `FlutterEngineGroup` share graphics context across multiple shells without re-probing.
5. Recommendation:
   - Recommend Option A (Hoisting decision to Android platform layer before `FlutterEngineInitialize`), utilizing `impeller::ContextVK` in the Android platform layer to extract Vulkan handles into `FlutterVulkanRendererConfig`.
6. Record `DR-0018` and verify formatting.
