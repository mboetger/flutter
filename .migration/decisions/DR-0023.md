# DR-0023: Platform-Owned Android Screenshot Architecture (Decoupling Rasterizer)

- **Status:** Accepted
- **Task:** T-1.15
- **Date:** 2026-09-16
- **Context:** Removing the internal `Shell` / `Rasterizer` coupling from Android screenshot capture (`FlutterJNI.getBitmap()`) without adding screenshot APIs to `embedder.h`.

---

## 1. Problem Statement
`FlutterJNI.getBitmap()` backs `FlutterView` bitmap capture, used by debug tooling, automated testing, and integration tests.
Historically, this path routed through internal engine classes:
`FlutterJNI.getBitmap()` → `AndroidShellHolder::Screenshot` → `flutter::Shell::Screenshot` → `flutter::Rasterizer::ScreenshotLastLayerTree`.

As part of the Android Embedder API migration, `AndroidShellHolder` is migrating away from `flutter::Shell` to wrap `FlutterEngine` (the public embedder C-API).
A previous migration attempt introduced `FlutterEngineScreenshot` and `FlutterEngineFreeScreenshot` (+563 lines) into `embedder.h`, but never called them, leaving `FlutterJNI.getBitmap()` returning `nullptr` and silently breaking frame capture.

We must define how Android takes screenshots in a post-migration architecture where `Rasterizer` is not accessible from platform code.

---

## 2. Considered Alternatives

### Alternative 1: Expose Screenshot in Embedder C-API (`embedder.h`)
- Add `FlutterEngineScreenshot` and companion `FlutterEngineFreeScreenshot` to `embedder.h`.
- Query `Rasterizer` inside `embedder.cc`.
- **Drawbacks:**
  - Violates the core architectural rule: *platform-agnostic → embedder API; platform-specific → platform code*.
  - Screenshotting is a platform-specific debug/test affordance. macOS does not need or use an engine API for screenshots; iOS expects to do the same.
  - Bloats `embedder.h` with complex memory lifetime management, format negotiations, and base64 encoding flags not needed by other embedders.

### Alternative 2: Keep Reaching into `Rasterizer` via Engine Internals
- Maintain an internal accessor or backdoor from `AndroidShellHolder` to `Rasterizer`.
- **Drawbacks:**
  - Defeats the purpose of the Embedder API boundary.
  - Prevents treating `FlutterEngine` as an opaque C-API handle.
  - Adds build-time dependencies that violate the dependency ratchet.

### Alternative 3 (Chosen): Platform-Owned Surface Readback
- Move screenshot responsibility to Android platform code: `AndroidShellHolder::Screenshot` queries `PlatformViewAndroid::Screenshot()`, which executes on the raster task runner and queries `AndroidSurface::Screenshot()`.
- Each `AndroidSurface` subclass reads directly from its active platform-owned rendering surface:
  - `AndroidSurfaceSoftware`: Reads raster pixels from `sk_surface_->readPixels(...)`.
  - `AndroidSurfaceGLSkia` & `AndroidSurfaceGLImpeller`: Makes the onscreen EGL surface current, obtains dimensions via `GetSize()`, executes `glReadPixels(0, 0, width, height, GL_RGBA, GL_UNSIGNED_BYTE, ...)`, and vertically inverts the row order to match Android's top-down bitmap representation.
  - `AndroidSurfaceDynamicImpeller`: Delegates to the active backing surface (`vulkan_surface_` or `gl_surface_`).
- **Benefits:**
  - Zero changes to `embedder.h`.
  - Zero calls into `Rasterizer` or `Shell::Screenshot`.
  - Architectural symmetry with macOS (`FlutterEngine.mm`), where screenshots read directly from the platform `IOSurfaceRef` via the platform view's surface manager without touching the engine core.
  - Clean separation of concerns: platform surfaces know their own format, stride, and coordinate orientation.

---

## 3. Decision
Adopt Alternative 3. Decouple `AndroidShellHolder` and Android platform code entirely from `Rasterizer::ScreenshotLastLayerTree`. Implement surface-level pixel readback across `AndroidSurface` subclasses and route through `PlatformViewAndroid`.
