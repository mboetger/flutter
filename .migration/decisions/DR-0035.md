# DR-0035: Extract Asset Resolver Setup into FlutterAssetResolver Shape

- **Status:** Accepted
- **Task:** T-2.6
- **Date:** 2026-09-16
- **Context:** Advancing Stage 2 (Refactoring & Decoupling) per `MIGRATION_LEDGER.md` §Stage 2 by extracting asset resolver setup into the `FlutterAssetResolver` shape introduced in T-1.3.

---

## 1. Problem Statement
In the Android embedder, asset resolution is performed by `APKAssetProvider`, which wraps Android's `AAssetManager` via `AAssetManager_open(..., AASSET_MODE_BUFFER)`:
- In `PlatformViewAndroidJNIImpl::RunBundleAndSnapshotFromLibrary`, an `APKAssetProvider` is constructed and passed to `AndroidShellHolder::Launch()`.
- In `AndroidShellHolder::BuildRunConfiguration()`, `apk_asset_provider_->Clone()` is registered with `RunConfiguration::AddAssetResolver()`.
- In `AndroidShellHolder::Spawn()`, `apk_asset_provider_->Clone()` is passed to the spawned shell holder.
- In `PlatformViewAndroidJNIImpl::UpdateJavaAssetManager`, hot-restart asset updates construct a new `APKAssetProvider` and invoke `UpdateAssetResolverByType(..., kApkAssetProvider)`.

To prepare for `FlutterProjectArgs` construction in T-2.8 and eventual Embedder API migration in Stage 3:
- The embedder must expose its asset resolution mechanism using the standard `FlutterAssetResolver` C-ABI structure established in T-1.3.
- `FlutterAssetResolver` defines callbacks (`get_asset_callback`, `is_valid_after_asset_manager_change`) and returns memory buffers through `FlutterMapping` with a `release_callback`.
- Stage 2 changes NO behavior: all existing Stage 0 characterization tests and internal `flutter::AssetResolver` pipelines must pass unmodified.
- Ratchet counts must remain `<= baseline` (deps <= 63, includes <= 123, nogncheck == 0).

---

## 2. Technical Solution

1. **`APKAssetProvider` C-ABI Shape Integration:**
   - Add `const FlutterAssetResolver* GetFlutterAssetResolver() const` to `APKAssetProvider`.
   - `APKAssetProvider` initializes and caches a `FlutterAssetResolver` structure:
     - `struct_size = sizeof(FlutterAssetResolver)`
     - `user_data = impl_.get()` (or pointer to `APKAssetProvider`)
     - `type = kFlutterAssetResolverTypeAPK`
     - `get_asset_callback`:
       ```cpp
       [](const char* full_path, FlutterMapping* mapping_out, void* user_data) -> bool {
         if (!user_data || !full_path || !mapping_out) return false;
         auto* impl = static_cast<APKAssetProviderInternal*>(user_data);
         auto mapping = impl->GetAsMapping(full_path);
         if (!mapping) return false;
         mapping_out->struct_size = sizeof(FlutterMapping);
         mapping_out->mapping = mapping->GetMapping();
         mapping_out->size = mapping->GetSize();
         mapping_out->user_data = mapping.release();
         mapping_out->release_callback = [](void* data) {
           delete static_cast<fml::Mapping*>(data);
         };
         return true;
       }
       ```
     - `is_valid_after_asset_manager_change`:
       ```cpp
       [](void* user_data) -> bool { return true; }
       ```

2. **Integration with `AndroidShellHolder`:**
   - Provide `const FlutterAssetResolver* GetAssetResolverForTesting() const` on `AndroidShellHolder` to allow verifying that the shell holder's active asset provider exposes the expected `FlutterAssetResolver` shape.
   - Preserves all internal engine `RunConfiguration::AddAssetResolver` and `Clone()` logic for Stage 2.

3. **Interoperability Verification:**
   - In `apk_asset_provider_unittests.cc`, verify that `FlutterAssetResolver` works seamlessly with `EmbedderAssetResolver` (from T-1.3).
   - Verify mapping lifetime: when `FlutterMapping` is consumed and released, `release_callback` properly deallocates the underlying `fml::Mapping` (closing the underlying `AAsset*`).

4. **Ratchet and Dependency Impact:**
   - `#include "flutter/shell/platform/embedder/embedder.h"` is an explicitly allowed header in `tools/android_embedder_deps.py` (`ALLOWED_HEADER_PREFIXES`).
   - Zero new GN dependencies required (`//flutter/shell/platform/embedder:embedder_headers` is already in `deps`).
   - Total internal includes and dependencies remain unchanged (<= baseline).
   - Zero nogncheck.
