# DR-0015 — I-7 raised and tiered; tests excluded from the diff cap

- **Status:** active
- **Date:** 2026-09-15
- **Decided by:** user (Matt Boetger), directive to the orchestrator
- **Supersedes:** the flat 400-line form of I-7 in MIGRATION_LEDGER.md §A.1 and MIGRATION_PLAN.md §2
- **Task context:** raised during T-0.15a plan review round 3

## Decision

I-7 becomes a **tiered** cap, and **tests are excluded from the count entirely**:

| Change class | Cap |
|---|---|
| Mechanical, tooling, or pure-refactor; alters no runtime behaviour | **≤ 3000 changed lines** |
| Alters rendering or runtime behaviour | **≤ 1000 changed lines** |

Excluded from the count in both tiers: generated files, pure deletions, **and tests**.

Tests must never be dropped, shortened, or merged to fit a cap. When a change exceeds
its cap the remedy is more branches — never fewer tests and never fewer controls.

## Why

**The flat 400-line cap was demonstrably too low and actively harmful.** On T-0.15a it
distorted five consecutive plan revisions:

1. `--allow-dirty` deferred "under I-7 limit" — a control removed to fit a number. That
   deferral was later found to break T-0.15a's self-verification entirely, because the
   pipeline always dirties the tree with its own `.migration/` artifacts and the tool
   refuses any dirty tree (`migration_verify.dart:119-123`).
2. Deleted lines credited as negative to offset additions — gaming the invariant itself,
   in the plan for the branch whose purpose is making such moves detectable.
3. A split proposed at exactly 395 lines against a 400 cap.
4. Tests silently dropped to hold that number.
5. Tests silently dropped again, after the orchestrator had removed the budget as a
   design variable in writing and set an explicit precedence order.

The cap also forced T-0.15a into a four-branch split whose only justification was the
line count rather than any coherent boundary of work.

**Why tiered rather than a flat 3000.** Review attention is not uniform. A 3000-line
mechanical rename is genuinely reviewable — the reader checks the pattern and spot-checks
instances. A 3000-line change to rendering or threading is not, because every line can
carry a behavioural consequence. A flat number would swap one blunt instrument for
another.

**Why tests are excluded.** A cap that discourages test coverage is worse than no cap.
Counting tests created direct pressure to write fewer of them, and that pressure was
acted on twice on a task whose entire purpose is preventing unverified work from being
certified.

## Consequences

- **T-0.15a collapses from four branches to one.** The split existed only to satisfy the
  400 cap. The full working tool — B1 artifact-opening, B2 environment inheritance,
  B3/DR-0013 smart dirty-tree, B4 zero-gate exit status, B5 clean unimplemented failures,
  plus `--audit-stack`, `--device-lock`, `--summary` and §A.7 device handling — belongs in
  a single coherent branch.
- T-0.15b, T-0.15c and T-0.15d as previously scoped are withdrawn.
- Line arithmetic in any in-flight plan must be recomputed against the new tiers.

## What does NOT change

- Absolute added lines, measured against the branch parent. No netting; deleted lines are
  never credit against additions.
- The precedence order stands: (1) the tool actually works, (2) every behaviour has an
  I-4 test, (3) the diff fits its cap. Satisfy (3) by adding branches only.
- Every requirement still carries at least one named test, including deferred ones, and
  the REQUIREMENTS × TESTS matrix remains mandatory.
