# DR-0019 — Decouple Static Renderer Configuration from Dynamic Surface Availability (Blocker B-2)

- **Task:** T-0.7
- **Branch:** android-embedder-v8/t-0.7-surface-lifecycle-spike
- **Author role:** implementer
- **Date:** 2026-09-15
- **Status:** accepted
- **Confidence:** firm

## Context
`MIGRATION_PLAN.md` Blocker B-2 and Open Question #2 identified that the Embedder API treats renderer configuration as static at `FlutterEngineInitialize`, while Android surfaces (`ANativeWindow`) are dynamically created, destroyed, and recreated across Activity transitions. In addition, iOS uses `Shell::SetGpuAvailability` to avoid background GPU execution. We must resolve whether renderer config replacement or surface availability is the proper abstraction and whether it can be shared with iOS.

## Options considered
| # | Option | Consequence |
|---|---|---|
| A | Replace `FlutterRendererConfig` mid-engine life on surface teardown/recreation | Causes destructive graphics context teardown, destroys cached pipelines, breaks Vulkan state, and complicates the Embedder API unnecessarily. |
| B | Decouple static renderer configuration from dynamic surface lifecycle & GPU availability; expose `FlutterEngineSetGpuAvailability` and `FlutterEngineNotifySurfaceDestroyed` | Keeps graphics context (`VkDevice`, `EGLDisplay`) permanent; presentation targets attach and detach dynamically. Shares GPU availability abstraction cleanly with iOS. Satisfies Criterion 5 & 6. |

## Tie-break
Evaluated against `MIGRATION_PLAN.md` §10.1:
- **Criterion 1 (Preserves behaviour):** Option B exactly matches Android's existing `NotifyCreated` / `NotifyDestroyed` mechanics and iOS's `SetGpuAvailability` behavior.
- **Criterion 5 (Generalization):** Option B directly generalizes across Android and iOS rather than creating an Android-only escape hatch.

## Decision
Adopt Option B. Renderer configuration remains static at `FlutterEngineInitialize`. Surface lifecycle and GPU execution permissions are treated as orthogonal axes. Stage 1 will add `FlutterEngineSetGpuAvailability` (T-1.1, shared with iOS) and `FlutterEngineNotifySurfaceDestroyed` / `FlutterEngineNotifySurfaceCreated` (T-1.2, synchronous teardown).

## What would change this decision
If iOS platform view architecture evolves to require destroying the Metal device context on backgrounding rather than suspending GPU command submission.

## Evidence
- `shell/common/shell.cc:2434` (`SetGpuAvailability`).
- `shell/platform/android/platform_view_android.cc:221-234` (`NotifyDestroyed` synchronous latch).
- T-0.2 characterization test suite passing in tree.

## Consequences
Stage 1 will implement tasks T-1.1 and T-1.2. The iOS review requirement is recorded in `HUMAN_REVIEW_REQUIRED.md` per §D.9.
