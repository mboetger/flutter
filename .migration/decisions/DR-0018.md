# DR-0018 — Hoist Vulkan/GLES Context Decision to Android Pre-Initialization (Blocker B-1)

- **Task:** T-0.6
- **Branch:** android-embedder-v8/t-0.6-graphics-context-spike
- **Author role:** implementer
- **Date:** 2026-09-15
- **Status:** accepted
- **Confidence:** firm

## Context
`MIGRATION_PLAN.md` Blocker B-1 identified that `AndroidContextDynamicImpeller` defers graphics backend selection until `SetupImpellerContext()` on the raster thread, while `FlutterEngineInitialize` requires static `FlutterRendererConfig` upfront. In addition, `FlutterVulkanRendererConfig` expects embedder-owned Vulkan handles (`VkInstance`, `VkDevice`, `VkQueue`). The previous v7 prototype avoided this by forcing OpenGLES/Software rendering unconditionally, which permanently broke HCPP (Invariant I-11).

## Options considered
| # | Option | Consequence |
|---|---|---|
| A | Hoist decision to Android platform layer before `FlutterEngineInitialize` | Evaluates system properties, SoC blacklist, and Vulkan dylib upfront. Extracts handles from `AndroidContextVKImpeller` into `FlutterVulkanRendererConfig`. Zero C-ABI expansion. Preserves Vulkan and HCPP. |
| B | Extend Embedder API with lazy/dynamic renderer config (`kDynamic`) | Requires public C-ABI expansion in `embedder.h` with complex asynchronous state machines in `embedder.cc`. Violates Criterion 5 & 6. |
| C | Invert ownership inside engine | Engine creates handles and exposes accessors. Complicates `FlutterEngineSpawn` shared context across shells. |

## Tie-break
Evaluated against `MIGRATION_PLAN.md` §10.1 criteria:
- **Criterion 5 (Generalization):** Option A directly aligns Android with iOS (`MTLDevice` passed to `FlutterMetalRendererConfig`) and desktop embedders.
- **Criterion 6 (Narrower API surface):** Option A requires zero new C-ABI fields in `embedder.h`.

## Decision
Adopt Option A. The Vulkan vs OpenGL ES selection moves to the Android embedder platform initialization prior to calling `FlutterEngineInitialize`. The Android embedder probes capabilities using `GetActualRenderingAPIForImpeller`, creates the shared `AndroidContext` (`AndroidContextVKImpeller` or `AndroidContextGLImpeller`), and populates standard `FlutterVulkanRendererConfig` or `FlutterOpenGLRendererConfig`. HCPP and Vulkan support are fully preserved.

## What would change this decision
If physical device profiling demonstrates that probing `libvulkan.so` on the platform thread causes a measurable (>10ms) regression on cold app startup that cannot be mitigated by caching or background initialization.

## Evidence
- Detailed architectural analysis and file:line citations in `engine/src/flutter/docs/android/graphics_context_ownership.md`.
- Re-verified that all driver check parameters (`ro.hardware`, `ro.product.model`, `ro.com.google.clientidbase`, `ro.vendor.mediatek.platform`, `ro.product.board`) are available synchronously via POSIX `__system_property_get` before engine initialization.

## Consequences
Downstream tasks T-1.11 (`FlutterEngineSpawn`) and Stage 2 (`AndroidShellHolder` restructuring) will construct `AndroidContext` before `FlutterEngineInitialize` and reuse it for spawned shells.
