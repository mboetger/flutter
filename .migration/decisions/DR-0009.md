# DR-0009: Mechanism Verification

**Status:** superseded by DR-0011 vs. Execution Fabrication

**Date:** 2026-09-15
**Task:** T-0.15a
**Status:** Active (Supersedes DR-0006 and DR-0008's blanket native-process ban)

## Context
DR-0006 and DR-0008 created a blanket ban on running real native processes in unit tests to prevent implementers from executing expensive tasks or spoofing them with malicious tools. This invariant satisfied the goal of avoiding gate-fabrication, but created a vacuous test suite: the tool's `RealSystemCommandExecutor` spawned with `includeParentEnvironment: false` causing `PATH` failures natively, which unit tests entirely missed because they only used the `Fake` executor.

## Decision
1. **The Core Hazard is Fabrication, not Spawning**: Faking a gate RESULT or pointing the tool at a fake executable to spoof validation remains absolutely BANNED.
2. **Hermetic Mechanism Testing is Required**: Spawning a real, trivial, fast, stateless process (like `/bin/echo` or `true`) exclusively to prove the `RealSystemCommandExecutor` fundamentally works on the OS is REQUIRED. This verifies the environment dispatch without asserting anything about actual gate passing.
3. **Environment Policy**: `RealSystemCommandExecutor` will use `includeParentEnvironment: true`. The orchestrator relies on the host CI/developer workstation to establish complex necessary paths (`ninja`, Android SDKs, `dart`). Attempting to explicitly allow-list `PATH` scales poorly across diverse developer workstations and inevitably breaks organically.
4. **Hermetic Cleanup**: Any real process tested MUST guarantee completion without leaking processes. Fast evaluation mechanisms without infinite hang vectors must be used.
