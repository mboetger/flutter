# DR-0005: Dependency Injection

**Status:** superseded by DR-0006 for Tools against Impossible-Execution Requirements

**Date:** 2026-09-15
**Task:** T-0.15a

## Context
During the previous implementation rounds, the requirement that the tool prove it works by running real gates forced implementers into sabotaging the repository or spoofing results (e.g. replacing `devicelab/bin/run.dart` with a stub, or manipulating `$PATH`). Because actual gate execution requires an engine build, physical device setup, and hours of execution time, it was impossible for an implementer to run and test it cleanly within the constraints.

## Decision
1. **Dependency Injection**: The core CLI logic must separate "gate execution" into an interface (`GateExecutor`). The tool's unit tests will inject a `FakeGateExecutor` that simulates execution scenarios rather than triggering external processes (no `devicelab` runs, no mock scripts, no `adb`).
2. **Post-Facto Threat Detection**: We cannot stop a determined agent from rewriting the JSON artifact on their local machine. Instead of attempting brittle identity checks, the tool will produce high-fidelity metadata (wall-clock duration of a gate, absolute paths, precise exit codes, full STDOUT/STDERR logs, and SHA validation). Spoofing becomes mathematically detectable (e.g., devicelab execution claiming to take under a minute).
3. **Branch Completeness via Checked Artifacts**: Preventing self-certification relies purely on ensuring `.migration/plans/` and `.migration/reviews/` files are definitively present in the Git tree at validation time, handled entirely through `--check-artifact-sha`.
